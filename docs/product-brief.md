# KeepTemp 产品初心与长期提示词

## 用户描述的起点

用户观察到：一些人共用 GPT、Claude 等 AI 账号，对话历史混在同一个平台账号里，工作内容、私人问题和思考过程容易被其他账号使用者翻看。为了减少普通历史中的暴露，他们会选择 Temporary / Incognito Chat。

由此出现一个矛盾：不希望对话留在共享历史，却希望自己还能找回、继续。关页、误操作、刷新、网络或浏览器故障，可能让一段已经投入很多轮思考的临时对话变得无法接续。

这是用户提供的需求假设和产品起源，不是经过市场调查的合购人数、使用频率或付费意愿结论。

## 核心任务

> 我希望对话不进入平台的普通聊天历史，同时在自己的设备上可靠保留文字，关闭页面后还能找回并继续；整个保存过程不需要我逐轮复制、整理或操作。

一句话：**平台里保持临时，本机上可以接续。**

目标体验：开启一次 → 在原网页照常聊 → 自动本地保存 → 随时找回 → 带上文字上下文继续新临时聊天。

“接续”不等于恢复原服务端 session：当前只恢复角色与文字。Saved 只证明当次持久化成功，不能保证未生成、未挂载或未提交的内容已经备份。

## 给后续产品与开发工作的提示词

你在维护 KeepTemp，一个帮助用户可靠保存和接续临时 AI 对话的本地优先浏览器扩展。

用户选择临时聊天，是希望避免对话进入平台普通历史；但他们并不总想把自己这段思考永久丢掉。KeepTemp 帮助他们同时保留临时聊天的使用习惯和自己找回文字的能力。

每次改动前，先判断它是否直接改善“自动保存、可靠找回、方便接续”中的至少一项。

- 自动保存是核心。不能把逐轮复制粘贴、整理角色或导入文件当成主流程，也不能把这种替代方案称为已完成核心需求。
- 保留原聊天习惯。授权后照常在平台网页聊天，不另造客户端，不要求注册、API Key 或后台服务。
- 可靠性比功能数量重要。消息不重复，会话不串，流式回复持续更新；写入失败必须真实可见，不能虚报 Saved。不确定是不是临时聊天时不捕获。
- 界面清爽。日常只需小状态标记、会话列表、搜索、阅读和接续；导出、暂停、排除、删除作为必要的数据控制。开发测试、诊断和模拟能力不出现在产品主流程。
- 本地优先。不上传、不接分析 SDK、不做云同步、账号系统、AI 摘要、Embedding 或复杂分类。
- 隐私承诺准确。平台普通历史、本机记录和平台端保留是不同的事情；共享账号并不因此获得真正的用户权限隔离。同一浏览器配置下的记录也不对其他本机使用者隔离。当前数据库未做应用层加密，不是密码保险库。
- 不承诺恢复原平台会话、附件、工具状态、隐藏状态或未观察过的历史。未提交尾部不作不会丢失的保证。
- 首版只做 Chrome + ChatGPT。Claude 和其他平台是未来方向，不因这个场景就提前扩张范围。
- 不读取用户私人聊天用于开发；回归验证使用独立浏览器和合成内容。测试通过与真实页面验收分别报告。

如果一个功能只能让插件看起来更完整，却没有让用户更省心地保住自己的临时对话，就先不做。

## 需求判断与验证

工程与产品判断：这是明确、可解释的用户痛点，尤其在用户已经用临时聊天、曾经丢失有价值的长对话时。它不限于共享账号，独立账号使用者也可能有相同需求。

尚未证明：高频用户规模、安装权限接受程度、与既有工具的差异是否足够、持续使用率、付费意愿。不用“很多人合购”替代市场验证。

优先找 5–10 位已有临时聊天习惯的用户，让他们讲最近一次真实丢失的对话，再观察是否愿意安装并持续使用。只统计自愿提供的反馈，不接入遥测或上传聊天。
